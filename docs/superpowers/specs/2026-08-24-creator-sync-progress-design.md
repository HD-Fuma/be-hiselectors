# 크리에이터 수집 TaskRun 진행률 설계

## 목표

YouTube 키워드 수와 Instagram 크리에이터 수를 하나의 숫자로 합산하지 않는다. 화면에 표시하는 크리에이터 수는 두 플랫폼 모두 실제로 신규 저장하거나 기존 정보를 갱신한 고유 크리에이터 수로 통일한다.

## 표시 기준

- YouTube 실행 중: `2개 키워드 중 1개 처리 · 크리에이터 7명 수집`
- Instagram 실행 중: `4명 중 3명 처리 · 크리에이터 3명 수집`
- 완료: `YouTube 7명 · Instagram 4명 수집`
- YouTube는 저장·갱신된 `creator_pool.id`를 실행 중 집합에 모아 중복을 제거한다. 검색됐지만 저장하지 않은 채널은 포함하지 않는다.
- Instagram은 저장·갱신 결과의 `instagramCreatorId`를 실행 중 집합에 모아 중복을 제거한다.
- 키워드 수는 YouTube 단계 진행률에만 사용하며 크리에이터 수와 합산하지 않는다.
- YouTube 키워드 분모는 quota와 실행 제한을 적용한 실제 실행 대상 수다.
- Instagram 분모는 빈 핸들을 제외한 실제 실행 대상 수다.

## 데이터 흐름

각 배치 서비스는 기존 반환값을 유지하면서 실행 중 snapshot을 받는 선택적 콜백 overload를 추가하고, 기존 무인자 메서드는 no-op 콜백으로 위임한다. YouTube 파이프라인은 키워드 하나의 DB 트랜잭션 안에서 저장·갱신된 `creator_pool.id`를 로컬 집합에 모은다. 트랜잭션이 성공적으로 끝난 뒤에만 그 ID 묶음을 배치 서비스에 반환하고 snapshot 콜백을 실행한다. 트랜잭션이 롤백되면 외부 ID 집합과 진행 문구도 증가하지 않는다. Instagram은 기존 결과의 `instagramCreatorId`를 사용한다. 배치 서비스는 실행 한 건 동안 ID 집합을 메모리에 유지해 고유 수집 인원과 현재 처리 위치를 계산한다.

`task_run`에는 nullable `VARCHAR(500)`인 범용 `progress_message` 하나만 추가한다. 진행률 기록기는 최신 문구를 기존 count flush와 함께 저장하며, 관리자 조회 응답은 이를 그대로 전달한다. 종료 문구도 실행 서비스가 마지막에 호출하는 `flush()`의 저장 대상에 포함해 유실되지 않게 한다. CREATOR_SYNC의 공용 `total/processed/succeeded/failed`는 종료 상태 판정에만 사용하고 플로팅 패널의 숫자나 퍼센트에는 사용하지 않는다. 패널은 `progressMessage`만 표시한다.

플랫폼별 실행 콜백은 다음 문구를 갱신한다.

- YouTube: 실제 실행 대상 키워드 수, 처리한 키워드 수, 고유 YouTube 크리에이터 수
- Instagram: 실제 실행 대상 수, 처리한 대상 수, 고유 Instagram 크리에이터 수
- 종료 전: 두 플랫폼의 고유 수집 수를 함께 표시하는 완료 문구

## 오류 처리

키워드 또는 크리에이터 처리 실패는 기존 공용 성공·실패 카운터와 TaskRun 종료 상태 판정에 반영한다. 이 공용 카운터는 서로 다른 단위가 섞이므로 CREATOR_SYNC 화면에서는 노출하지 않는다. 실패 한 건을 수집한 크리에이터 수에 더하지 않는다. 전체 작업 예외와 STALE 판정은 기존 로직을 유지한다.

## 제외 범위

- 별도 진행률 라이브러리나 새로운 실행 프레임워크를 추가하지 않는다.
- 고유 ID 집합은 실행 도중에만 메모리에 유지하고 별도 상세 이력 테이블로 저장하지 않는다.
- 리포트 생성 TaskRun은 이번 변경에 포함하지 않는다.

## 검증

- YouTube 키워드 수와 크리에이터 수가 합산되지 않는 단위 테스트
- 동일 크리에이터가 반복 처리돼도 플랫폼별 수집 인원이 한 번만 증가하는 단위 테스트
- 실제 실행 대상만 단계 진행률의 분모로 사용하는 단위 테스트
- 진행 문구가 기존 flush 주기에 맞춰 저장되고 관리자 조회 응답에 포함되는 테스트
- 실행 중·완료 문구를 검증하는 프론트엔드 테스트
